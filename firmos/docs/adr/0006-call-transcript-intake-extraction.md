# ADR-0006: Call-transcript intake extraction (Google Meet notes -> intake autofill)

**Status:** Accepted (2026-09-11) · **Builds on:** ADR-0005 (single-tenant parity rebuild)

## Context

Jason onboards bookkeeping prospects over Google Meet with Gemini "Take notes for me" running. His #1 pain point (requirements breakdown §2) is manual intake entry during live calls: the conversational wizard's questions get asked and answered on the call, then typed in again afterwards. The Gemini notes doc has a fixed export format (`📝 Notes` summary with `(HH:MM:SS)` citations, then a `📖 Transcript` block of speaker-labeled verbatim lines) and exports from Drive as `.docx`.

The whole game is hallucination control: an autofill that invents answers is worse than no autofill. Nothing may reach `client_intakes` without a human confirm, and the existing review screen / purgatory queue / manager-gated conversion stay as the final verification layer.

## Decision

1. **Manual upload/paste ingestion first.** A dialog on the intake list accepts pasted text or a `.docx`/`.txt` upload. No Google OAuth, Drive scopes, or Gmail plumbing in v1: Drive export requires restricted scopes with a Google security review, and the Google Meet REST API's structured transcripts require a Workspace org. Phase 2 (Drive-folder auto-import via Vercel cron, or the Gemini-notes-email -> Gmail filter -> webhook listener variant discussed on the 2026-08-20 call) is deferred until the manual loop proves out.
2. **Gemini API for extraction** (`@google/genai` SDK, key from Google AI Studio). Single tenant, one shared key (`GEMINI_API_KEY`), no per-user OAuth. Structured output via `responseMimeType: application/json` + `responseSchema`; model from `INTAKE_EXTRACT_MODEL` (default `gemini-3.5-flash`, the current flash-class; `gemini-2.5-flash` shuts down 2026-10-16). Non-string values travel JSON-encoded inside the schema's string `value` field and are decoded deterministically by the coercion layer. Repo precedent: foodcart-saas's Bedrock wrapper (system-prompt-constrained JSON, schema-validated response, deterministic fallback).
3. **A deterministic stub extractor stands in whenever `GEMINI_API_KEY` is absent or `INTAKE_EXTRACT_MOCK=1`.** It is a conservative line-pattern matcher tuned to the synthetic onboarding fixture; it keeps CI and e2e hermetic and gives dev a working loop at zero API cost. It is not expected to be right on arbitrary calls - on the real dev-strategy-call fixture it surfaces only a few ambiguous example-mentions and no client facts.
4. **Evidence-required output contract + hand-rolled coercion.** Every extracted field carries a verbatim `evidence` quote and a `confidence` 0-1; fields without evidence are omitted, never guessed. The coercion layer (no Zod, per house style) type-checks each value against the intake vocabulary sourced from the wizard's question registry (canonical service keys, enum option sets), folds near-miss enums to canonical values, rejects invalid values with reasons, clamps confidences, and validates arrays element-wise. The `missing` list (required wizard keys with no evidence) is computed deterministically, never delegated to the model.
5. **A pre-draft review screen is the human gate.** Fields are grouped by wizard chapter with confidence badges in the mandate's status colors (green >=0.9 auto-checked, amber 0.6-0.9, red <0.6 unchecked), expandable evidence, per-row accept/edit/discard, an accept-all-high-confidence bulk action, and the missing list rendered as "still to ask the client". The suggested legal name seeds the required name field with a duplicate check via the existing `checkDuplicates`.
6. **Confirm creates the draft through the existing intake machinery.** The confirm action re-coerces every accepted field server-side, builds the patch via the registry's own `buildPatch`, and calls `createIntake` - the same engine function `saveIntake` uses - in one atomic step (a `saveIntake`-then-link pair was rejected: it can leave a half-created intake when linking fails). Provenance rides in `form_data._extraction` (`{ transcriptId, model, confirmedBy, confirmedAt, fieldConfidences }`) through `IntakeFormData`'s open index signature - no change to the intake schema. The wizard's existing `firstUnansweredScreen` resumes at the first question the call did not answer; status flow, review, and conversion are untouched.
7. **New `intake_transcripts` table** (`id`, nullable `intake_id` set on confirm, `file_name`, `storage_key`, `char_count`, `model`, `extraction` jsonb, `status` uploaded|extracted|confirmed|failed, `created_by_id`, timestamps). Raw text is stored through the existing §13 storage drivers (local / Vercel Blob private) under `IntakeTranscripts/`; uploads pass the existing §13 validation layers. Transcripts hold prospect financial PII: every action is staff-gated like the other intake actions, and retention follows the documents pattern.

## Consequences

- Two new dependencies: `@google/genai` (extraction) and `mammoth` (docx -> text; the boring standard parser). Both are dynamically imported server-side so neither enters a client bundle.
- Extraction runs inline inside the import server action (one LLM call, a few seconds). If that ever outgrows action timeouts, the row's `uploaded`/`failed` states plus the retry action already support moving it to an Inngest job without schema changes.
- The stub's patterns are fixture-tuned by design; when the wizard vocabulary changes, `EXTRACTION_FIELDS` in `src/server/intake-extract.ts` is the single place to update (it reads the registry's label maps).
- `docs/CALL-NOTES-IMPORT.md` documents the operator flow and env vars.
